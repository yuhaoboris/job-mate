## 问题列表

### G01 · 重要：组合决定完成第一个动作后，就跳过尚未执行的回复

- **位置：** `skills/followup/SKILL.md:60-76`；`scripts/ledger.py:747-760`。
- **问题：** `decision` 以任意一个完成观察或任意一次 sent 判断整个决定完成，无法表示同一决定还有后续动作。
- **触发场景：** 本人明确要求「交还会话并回复面试时段」，这是技能第 65 行自己的例子。Agent 先按表记带同一 decision 的 released；随后执行回复前查询 decision，已经得到 done，于是按第 73 行只补「已执行」，不发送回复。**不需要发生崩溃即可触发。** 如果交还之后中断，下轮对账还会按 done 解除暂停，使漏发更难察觉。
- **验证：** 临时工作区先有 manual/paused，追加 released 后，decision 从 `not_started` 变为 `done`，但 `attempts: []`，没有发生任何外发。多个外发动作共用一个 ID 时也有相同结构问题：第一次 sent 就令整个决定 done。
- **建议：** 完成条件必须对应本人要求的全部动作。对于「本地交还 + 回复」，外发完成只能以对应回复的 sent 为依据，released 只能表示前置步骤完成；支持多个外发时，为各动作提供可区分的执行状态，全部完成后再结束整个决定。不要仅把 released 从完成集合移除，却仍用任意 sent 判定多条消息全部完成。
- **补测：** 无中断的「交还 + 回复」；交还后中断再恢复；一条决定包含回复和发简历。既验证不重发，也验证后续动作不会被漏掉。

### G02 · 重要：job_closed 可经 declined → reopened 间接解除

- **位置：** `scripts/ledger.py:578-581`；`skills/followup/SKILL.md:98-105`；`shared/ledger.md:91`。
- **问题：** 关闭原因直接被最新关闭观察覆盖；因此“reopened 对 declined 以外的结束状态无效”只在直接相邻的转换下成立。
- **触发场景：** 会话先因旧职位关闭记 job_closed；HR 后来推荐一个薪资不符的新职位，按第 98 行先评估，再记 declined，覆盖了 job_closed；HR 再推来符合条件的职位，reopened 清除 declined，普通回复检查放行。这个序列不需要误填事件或手工篡改文件。
- **验证：** 依次追加 `job_closed → declined → reopened`。初始 `check --kind reply` 返回 closed 阻止；最后 `threads.closed` 为 null，check 返回 `allowed: true`。本次放行复现针对 job_closed；rejected/risk 另有公司级检查，不能据此声称风险公司也会被放行。
- **建议：** 按当前已写明的规则，保留不可自动重开的关闭原因，不让 declined 覆盖它；技能也应在评估新职位之前区分可重评的 declined 与其他终止状态。若产品希望 job_closed 后允许处理新职位，应明确改规则，而不是依赖中间恰好出现一次不合适职位才能重开。
- **补测：** job_closed 后直接 reopened，以及先 declined 再 reopened，都应符合相同的关闭策略。现有测试只覆盖 rejected 后直接 reopened，未覆盖中间状态覆盖。

### G03 · 一般：恢复孤立暂停事项时，CLI 不返回所需的暂停原因

- **位置：** `skills/followup/SKILL.md:46-47`；`scripts/ledger.py:751-770`、`:563`；`shared/ledger.md:3`。
- **问题：** 技能要求根据暂停记录的 reason 补建 inbox，但现有查询命令不提供这个字段，同时约定事件记录只经 ledger.py 读写。
- **触发场景：** 已追加 paused，在创建 inbox 事项前中断。下一轮 threads 能看到决策 ID，公司与招聘者也可查到，但不知道暂停的问题是什么；decision 的 observations 仅列出完成观察，不含 paused，stillPausing 也只有公司和招聘者。Agent 无法按文档给定的查询接口执行这一步，只能临时绕开读取约定或再要求本人提供原因。
- **验证：** 给 paused 写入一段唯一的虚构 reason；查询 threads、decision、validate、stats，输出均不包含该 reason。原始事件里确实存在它，问题是没有暴露所需的只读查询能力。
- **建议：** 在 `decision --id` 返回相关 paused 记录的 reason、时间、平台、公司和招聘者，或新增按决策 ID 查询观察的只读命令。恢复时只使用已有最小摘要，不臆造问题、选项和截止时间。
- **补测：** 只写 paused、不创建 inbox，随后仅通过公开 CLI 输出即可重建含原始问题摘要的事项。

### S01 · 建议：收窄 guard 的绝对保证表述

- **位置：** `docs/design.md:258`；`scripts/ledger.py:776-790`、`:963-965`。
- **问题：** 文档说“guard 会续期 60 分钟，接管不会在这个窗口内发生”，超出了两次独立工具调用能保证的范围；实现实际沿用锁的 ttlMinutes，也不一定是 60 分钟。
- **触发场景：** guard 和 UI 点击并非原子操作，调用间或 UI 工具内部仍可能暂停。当前“等待、卡顿或超时后重读页面再 guard”的规则已经提供实用防护，但不能把它描述成对任意进程停顿的数学保证。
- **建议：** 写成“guard 按当前租期续期；正常连续执行时缩小过期接管窗口，任何中断恢复必须重新检查”。若未来要求严格的系统级隔离，再考虑执行器层的互斥。本建议不重新打开上轮 F01，也不单独阻断实测。
