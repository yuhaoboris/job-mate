## R1：P1 进程组清理只等主进程，后代仍可能继续执行

位置：scripts/notify.py:805–814、843–865。

已复现：启动同一进程组中的父子两个 Python 进程；父进程正常响应 SIGTERM，后代先安装 SIG_IGN 再写就绪标记。调用 _stop_child(proc, grace=0.2) 后，父进程 returncode=-15，但 os.kill(后代PID, 0) 仍成功。复现结束后由审查脚本 SIGKILL 清理了自己创建的进程组。

原因：只有 proc.wait 超时才发送 SIGKILL；主进程先退出就不会检查残留的进程组。另一个路径是主进程非零退出：launch_agent 将状态改为 failed，但没有调用进程组清理，与文档所称失败也清理不一致。残留工具进程可能在监听器认为结束后继续工作。

修复要求：以整个受管进程组为清理对象，主进程已退出仍检查和终止残留后代；停止、超时、异常退出路径统一收尾。测试需要真实的忽略 SIGTERM 的后代，不能只检查 Agent 主 PID。清理逻辑不得误杀其他进程组。

## R2：P1 ready 生命周期在技能中没有完整闭合

位置：skills/followup/SKILL.md:30、49–61、90–93；shared/notify.md:79–82。

置信度：静态控制流已确认；未用真实 Agent 演练。

1. 全局暂停在准备步骤被归入“本轮按禁发处理”，新增规则又要求“本轮禁发”将 ready 标 consumed。暂停时显式运行 followup，或执行期间收到暂停，就可能把可恢复任务消费掉；之后恢复/重试不再唤起。实现说明说全局暂停保留 ready，但技能没有这条例外。
2. “待处理”答复按 shared 第4步改为“已处理”并标 ready，第5步进入 followup 2.2；而2.2仅处理“已决定且 ledger != done”，没有“已处理”收尾路径，ready可能反复唤起直至耗尽次数。
3. ledger 已记 unpaused/done，但在 done 通知或 consumed 前中断：下一轮同样被2.2的 done过滤跳过，缺少明确的 ready 对账、结果通知补发和 consumed 收尾路径。

修复要求：明确区分全局临时暂停与本人本轮禁发；前者保留 ready。对“已处理、无需后续动作”和“ledger 已done但队列未收尾”增加明确路径；后者只能补状态/通知，不能重发HR消息。结果通知复用稳定正文和键。禁止把所有旧 consumed 自动重入。增加使用真实 notify/ledger 状态的临时工作区演练，验证全局恢复后的可执行性和完成后的不再唤起；若仅是文档约束，准确说明测试边界。
