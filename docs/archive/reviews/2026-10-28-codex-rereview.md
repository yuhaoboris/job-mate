## 剩余问题

### F01 · 严重：pending 已成功之后失锁，旧任务仍可继续 UI 外发

- **位置：** `scripts/ledger.py:798-804`；`skills/apply/SKILL.md:101-106`、`:122`；`skills/followup/SKILL.md:123-133`；`docs/design.md:256`。
- **问题：** 持锁检查只保护「写入新的 pending」，并没有覆盖 pending 成功与实际点击发送之间的暂停和恢复。
- **触发场景：** A 已写 pending，准备执行下一次 UI 工具调用；A 因进程暂停、长时间等待等原因超过租期。B 接管，把该 pending 改记 uncertain，并开始处理其他会话。A 恢复后沿技能顺序执行点击/输入/发送，无需再经过任何持锁或 attempt 状态检查。这样两轮可能同时操作同一浏览器；B 不重发 uncertain 尝试，并不代表 A 不会继续发送。
- **验证：** 临时工作区中，A 的 pending 追加返回 0；令其锁过期后，B 获取返回 0，`reconciled` 包含 A 的尝试，当前持有者为 B。技能下一步仍是 UI 操作。只验证了本地状态和指令路径，未执行实际 UI 外发。
- **建议：** 为已创建的 attempt 提供「仍由本 run 持锁、仍处于可发送状态」的检查；将其用于每个可能外发的 UI 操作前。发生暂停、超时或恢复后必须重新检查当前页面和原 attempt，不沿用先前 pending 成功的结果继续发送，也不新建尝试绕过 uncertain。设计中的「旧任务无法写新 pending，因此不会同时外发」结论应收窄，直到这条路径也受约束。

### F02 · 重要：restore 检查完锁后，新任务仍能在配置恢复期间启动

- **位置：** `scripts/workspace.py:324-342`、`:344-361`。
- **问题：** `running_lock()` 离开协调锁之后，restore 才备份和复制配置；它没有取得自己的运行锁，形成检查与使用之间的竞态。
- **触发场景：** restore 检查时无人持锁；接着 followup 成功获取运行锁并读取配置；restore 继续覆盖 profile、candidate、qa 等文件。任务可能读取到前后版本混合的配置，或按已被恢复撤销的授权继续执行。另外，现有逻辑对所有 setup 锁都忽略，也不能区分是不是另一个正在改配置的 setup。
- **验证：** 在 restore 完成 `running_lock()`、进入 `before-restore` 备份前，安排独立 CLI 进程获取 followup 锁。结果 followup `acquired: true`，restore 仍返回退出码 0 且规则文件被恢复，当前锁属于该 followup。插桩只控制调度时点，没有替换锁判断结果。
- **建议：** 恢复全过程占用同一运行互斥机制，先取得属于本次恢复的锁，再备份和写入，结束释放。若复用 setup 的锁，必须显式核对 runId；不能因为持锁技能名是 setup 就默认允许。

### F03 · 重要：筛掉的新入站会话，下轮会绕过职位筛选

- **位置：** `skills/followup/SKILL.md:72-83`、`:99-106`；`scripts/ledger.py:543-553`、`:696-718`。
- **问题：** 新入站职位明确不符时只记 skipped；这条记录会让它下一轮变成「已登记会话」，不再进入职位筛选，也没有暂停或结束状态。
- **触发场景：** 新 HR 的职位薪资不符，第一轮按 4.2 节不回复并写 skipped。第二轮 HR 对同一职位索要简历，因本地已有记录进入 4.3 节；没有「另一个职位」触发重新筛选，最新消息也未再次陈述薪资不符，于是命中索要简历并可发送。若不符项是单休，4.3 新增的停止名单分支也没有在首次 4.2 筛掉时执行。
- **验证：** 写入 `reply/skipped`（reason 为薪资不符）后，`threads` 返回该会话、`closed: null`；`check --kind resume` 返回 `allowed: true`。这符合当前技能的跨轮执行路径。
- **建议：** 区分「已记录」与「已评估且允许推进」。明确不符的职位应持久化不可推进状态，或每次发送前核对当前职位的有效筛选结果；涉及已定停止名单条件时，在 4.2 分支也按规则停止。换职位后可以重新评估，但不能因一次 skipped 自动获得推进资格。

### F04 · 重要：所有未开始的决定都被导向发送，遗漏非发送类决定

- **位置：** `skills/followup/SKILL.md:45-54`、`:74`；`shared/notify.md:22`；`scripts/ledger.py:742-757`。
- **问题：** `not_started` 一律要求「按第 5 节发送」，没有处理只需写本地观察事件或更新配置的决定。
- **触发场景：** 本人批准「把这个旧会话交给 Agent」，正确动作应先记 released；或本人只写「解除暂停」、要求仅更新问答库而不回复 HR。这些事项没有外发 attempt，查询永远返回 not_started，但第 2 节将它们导向向 HR 发消息。Agent 要么卡住，要么自行臆造一条回复，无法按技能完成正确闭环。
- **验证：** 只有 paused 观察的决策查询返回 `not_started`，建议明确写着「可以按发送流程执行」。旧会话交还和直接解除暂停都是当前技能/通知文档明确支持的输入，并非额外功能要求。
- **建议：** 先区分决定的动作类型：外发、本地交还/解除暂停、更新口径或附件状态、继续保持暂停等。只有外发类查询发送尝试并进入第 5 节；其他类型执行相应本地动作后记完成，禁止为获得 done 而制造消息。

### F05 · 重要：inbox 与暂停事件分开写，恢复时没有对账

- **位置：** `skills/followup/SKILL.md:41`、`:51-54`、`:113`；`shared/notify.md:21-23`；`scripts/ledger.py:568-574`。
- **问题：** 「待决定/已执行」与 paused/unpaused 分属两个文件，当前恢复流程不能修复两次写入之间中断导致的不一致。
- **触发场景 A：** 已向 inbox 写入需暂停整个会话的待决定事项，但在追加 paused 前中断。下轮明确读取的是「已决定」事项，发送检查也只读 ledger，因此整个会话可能继续自动回复。
- **触发场景 B：** 已发送成功，在 inbox 补好「已执行」，但追加 unpaused 前中断。下轮因已经注明已执行跳过该事项，遗留 paused 使会话一直无法回复，即使 `ledger decision` 已是 done。
- **验证：** 构造场景 B 的正常中间状态：decision 返回 done，inbox 有已执行标记，普通 reply 检查仍被 paused 拦截；按第 41 行筛选该事项不会进入恢复处理。场景 A 是相反的双写缺口，不需要绕过任何状态校验。
- **建议：** 让决策完成与暂停状态有一个权威持久来源，inbox 作为其展示；或在每轮开始对全部未决事项、已完成但仍暂停的事项做幂等对账。单纯交换两次写入的先后顺序会改变缺口方向，不能解决恢复问题。

### F06 · 重要：同一 jobId 换公司显示名后，首次联系检查会放行

- **位置：** `scripts/ledger.py:673-683`。
- **问题：** 新实现先要求公司名匹配，否则 continue，导致后面的同一 jobId 判断无法执行。这是相对上轮代码的回归。
- **触发场景：** 某职位已有 pending、uncertain 或 sent，后来同一平台、同一职位链接显示了不同且不互相包含的公司名（如品牌名和登记名）。即使 jobId 完全相同，check 仍放行；这让最明确的职位标识依赖较弱的显示名称。
- **验证：** 写入公司「品牌名称」、`jobId=same-id` 的 uncertain；用公司「登记公司」、相同 jobId 查询，返回 `allowed: true, reasons: []`。这里验证的是输入组合下的确定性行为，不声称平台已经发生过名称变更。
- **建议：** 同平台相同 jobId 应优先拦截，与公司名是否匹配无关；公司名只参与公司去重、疑似重发及缺失 ID 时的兜底。补测相同 ID、不同公司名的 pending/uncertain/sent。

### F07 · 重要：旧批准无条件越过后来发生的本人接管

- **位置：** `scripts/ledger.py:707-708`；`skills/followup/SKILL.md:57`；`docs/design.md:229`。
- **问题：** 只要传入 decision，manual 就不阻止回复，未区分批准发生在接管之前还是之后，也未要求本人明确交还。
- **触发场景：** 本人此前批准一条面试回复但尚未执行；随后亲自接手会话，本地已记 manual。下一轮仍执行旧 inbox 决定，check 直接跳过 manual，技能第 57 行也明确允许执行。这不是「接管后本人又明确要求本次代发」，而是让历史批准覆盖更新的接管状态。
- **验证：** 先记带决策 ID 的 paused，后记 manual；用相同 decision 检查 reply，返回 `allowed: true`。当前事件和 inbox 没有用于核对批准新旧顺序的统一机制。
- **建议：** 按当前设计，manual 后等待明确交还，再处理旧批准。若要允许接管状态下的一次性代发，必须有接管后针对该动作的新授权及可核对的关联，不能仅靠任意非空 `--decision` 绕过。上轮报告要求的也是「明确交还或针对本次动作的新授权」，不是所有旧决定均有效。

## 需要本人决定的问题

上轮三个取舍已在修改记录中给出答案，本轮不重复询问：未证实排除项可沟通后核实、待决定暂停整个会话、恢复保留后来新增的停止项。

唯一仍存在的策略分歧是 **manual 接管与一次性代发的关系**：当前设计仍写「直到本人明确交还」，技能却允许任何已决定事项越过接管。若没有新的明确产品决定，按设计执行即可；如果希望保留一次性代发例外，应限定为接管后针对该动作的新授权，而非历史批准自动生效（F07）。这不是让修复等待批准，而是不能用实现中的例外替代已确认的设计。

F02 的确定性交错：restore 执行完 `running_lock()` → 在 `do_backup(..., 'before-restore')` 入口暂停 → 独立 CLI 执行 `ledger lock acquire --skill followup` 并确认成功 → 恢复 restore；当前实现会继续覆盖配置并成功返回。

下一轮验证应覆盖「两轮运行」和「中断点」：新入站筛掉后再次来信、非发送决定执行、已执行标记与 unpaused 之间中断、pending 后暂停再失锁、restore 检查后新任务加锁。现有 42 个测试通过不足以证明这些完整路径成立。
