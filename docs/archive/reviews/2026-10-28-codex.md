## 总体结论

**暂不建议进入真实外发实测，可以继续离线验证与只读筛选。** 最大风险是「已决定事项」绕过统一发送检查，以及过期锁无法保持唯一执行者：前者有中断后重复发送、无视本轮只读限制的路径，后者可能让两个任务同时操作同一浏览器。现有 26 个测试全部通过，但没有覆盖这些路径，且一个测试把危险的 `pending → skipped` 转换当作正常行为。以下列出 14 项问题：严重 4 项、重要 8 项、一般 2 项。未将已确认的产品原则、打包/CI、通知配置或尚未实测本身列为缺陷。

评审范围：指定的设计、三个技能及平台说明、全部 `shared/`、两个脚本和测试。未访问招聘平台，未发送消息，未读取或修改真实 private-job-workspace 工作区。代码验证全部使用临时目录和虚构数据；仓库只新增本报告。

验证命令：`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests`，结果为 `Ran 26 tests ... OK`。下文「已复现」指本地脚本结果；技能执行顺序问题通过静态路径分析确认，不代表已在平台触发。

## 问题列表

### R01 · 严重：已决定事项没有可恢复的执行标识，中断后可能重复外发

- **位置：** `skills/followup/SKILL.md:35-40`、`:84-89`；`shared/notify.md:20-22`。
- **问题：** 是否执行仅看 inbox 是否写了「已执行」，没有把决策 ID 与外发 `attemptId` 绑定，也没有在执行前经过第 4 节分诊。
- **触发场景：** 本人批准一条回复，Agent 已发送并追加 `sent`，但在给 inbox 补「已执行」之前中断。下轮仍把它视为未执行，直接进入第 5 节，生成新的 `pending` 再发一次。若中断时只有 `pending/uncertain`，同一路径也没有先查 `unresolved`。此外，本地已经 `manual=true` 的会话仍可能被旧决定直接驱动发送。
- **依据：** 第 5.1 节只有「出现新消息则重新分诊」，没有无条件检查历史尝试、接管状态和决策是否已执行。没有新消息时不会补上这些检查。
- **建议：** 发送前持久化 `decisionId → attemptId`；恢复时 `sent` 只补 inbox 标记，`pending/uncertain` 只核对，不创建新尝试。所有发送入口都先经过统一检查，包括已决定事项、简历请求和主动跟进；接管后只有明确交还或针对本次动作的新授权才执行。

### R02 · 严重：「L1 也执行」会覆盖本轮明确的禁止发送

- **位置：** `skills/followup/SKILL.md:25`、`:31-39`、`:78`；`shared/safety.md:7`。
- **问题：** 技能一方面规定「只看看」降为 L1、L1 不发送，另一方面又要求已决定事项在 L1 下发送，没有区分长期 L1 与本轮禁止发送。
- **触发场景：** inbox 中有此前批准、尚未执行的面试回复；本人这轮说「只看看，这次别发」。第 2 节仍要求「L1 也执行」，Agent 可以据此发送旧批准内容，违反本轮限制优先的已定规则。
- **建议：** 把本轮禁发单独作为最高优先级条件，在所有发送入口检查。历史批准只提供动作授权，不能覆盖后来给出的本轮禁发指令；无需改变默认 L2。

### R03 · 严重：并发接管同一把过期锁时，两个任务都能成功

- **位置：** `scripts/ledger.py:666`、`:684-704`。
- **问题：** 读取旧锁、回收事件、删除锁和创建新锁不是一个互斥操作；`O_EXCL` 只保护最后的创建。
- **触发场景：** A、B 同时读到过期锁 X；A 删除 X 并创建自己的锁；B 随后执行第 689 行，删除的是 A 的新锁，再创建 B 的锁。A、B 都收到 `acquired: true`，都可以进入外发流程。
- **验证：** 已用两个独立进程复现。测试仅在「都读完旧锁」和「B 执行 unlink」处控制调度顺序，未修改锁判断结果。A、B 均返回退出码 0、`acquired: true`，最终文件属于 B。
- **建议：** 用不被删除的独立协调锁串行化完整的读取、接管、释放过程；在临界区内重新核对持有者。增加上述交错顺序的并发测试，不能只测顺序调用 acquire。

### R04 · 严重：锁过期后，仍在运行的旧任务不会失去发送资格

- **位置：** `scripts/ledger.py:457-490`、`:694-696`；`skills/apply/SKILL.md:49`、`:78-99`；`skills/followup/SKILL.md:26`、`:87-107`。
- **问题：** 锁只有固定过期时间，没有续期；外发前和追加 `pending` 时均不验证当前 `runId` 是否仍持锁。
- **触发场景：** A 处理时间超过 60 分钟或暂停后恢复，B 按规则接管过期锁。A 继续读页面、检查额度、追加新的 `pending` 并操作浏览器。接管时处理的只是当时已有的 pending，挡不住旧任务之后新建的尝试。即使修好 R03，此路径仍然存在。
- **验证：** 无需并发调度即可复现：A 用 `--ttl 0` 获取锁，B 接管，随后以 A 的 `runId` 追加 `pending`，返回退出码 0，而当前锁属于 B。
- **建议：** 提供续期和持有者校验；新 `pending` 必须由有效持锁者创建。技能在每个可能外发的动作之前确认有效锁，失锁或续期失败立即停止；不能只检查本轮开始时拿到过锁。

### R05 · 重要：状态转换未校验，未决发送可被普通记录解除，额度也能退回

- **位置：** `scripts/ledger.py:348-365`、`:484-489`、`:501-505`；`tests/test_ledger.py:97-103`；`shared/ledger.md:49-59`。
- **问题：** 除 `sent` 外，尝试状态完全取最后一行；`append` 只查相同 ID 是否出现过，不校验合法转换及人工核对要求。
- **触发场景：** 已写 `greet/pending` 的尝试被追加同 ID 的 `skipped`，`check` 就允许重发，`quota` 也不再计数；已 `uncertain` 的尝试可由 `skill=apply` 直接追加 `failed_no_send`，下一轮即放行。这与「未决状态阻止外发直到人工核对」「pending 即占额度、不补量」冲突。
- **验证：** 两种转换均已复现。第一种返回 `allowed: true`、`greetsToday: 0`；第二种非人工解除返回退出码 0，下一轮 `allowed: true`。现有测试反而明确断言第一种转换后应放行。
- **建议：** 校验尝试的转换序列和不可变身份字段；`skipped/already_contacted` 应作为未执行动作的独立记录，不能清除已有 pending。解除 `uncertain` 需人工确认记录；额度按「是否曾写 greet/pending」计数。脚本可验证记录约束，人工授权的真实性仍由技能负责。

### R06 · 重要：公司去重只看 greet，漏掉由 followup 建立的联系

- **位置：** `scripts/ledger.py:416-418`；`docs/design.md:121-122`。
- **问题：** `check` 完全过滤掉 `reply/intro/followup/resume`，把没有 greet 的已联系公司当作未联系。
- **触发场景：** HR 主动来信，本人交给 Agent 后由 followup 回复，因此本地只有 reply，没有 greet；随后 apply 搜到同公司另一个招聘者的职位，新职位页面仍可能显示「立即沟通」。默认公司去重应拦截，实际会放行。若前一次回复是 pending/uncertain，`check` 同样看不到。
- **验证：** 在空临时工作区仅写一条 `reply/pending`，同公司 `check` 返回 `allowed: true`；源码对 reply/sent 也采取相同过滤。页面「继续沟通」仍能挡住已有会话，但不能代替跨招聘者的公司去重。
- **建议：** 明确区分「首次联系去重」和「会话可否回复」检查。apply 的公司去重应纳入其他动作已建立的联系及未决尝试；不要把所有 sent 直接用于阻止正常的 followup 回复。

### R07 · 重要：inbox 中的暂停决定没有进入后续发送检查

- **位置：** `shared/notify.md:10-21`；`skills/followup/SKILL.md:37`、`:54-74`；`scripts/ledger.py:539-556`。
- **问题：** inbox 可以写「该会话不再自动回复」，但技能只明确读取「已决定」事项，分诊和 `canFollowup` 都没有待决定暂停条件。
- **触发场景：** 一次面试邀约被上报，inbox 明确暂停该会话；本人尚未答复，HR 又问一个 qa 中有口径的问题。下一轮照表可直接回复。L3 也可能把最后由我方发言的暂停会话再次列入跟进候选。
- **建议：** 暂停应带稳定的会话标识和动作范围，并在所有外发前读取、核对。待决定事项完成或本人明确解除时才解除对应暂停。是否暂停整个会话还是特定承诺，由产品策略决定，但已写出的暂停范围必须执行。

### R08 · 重要：简历直接送达分支没有关闭 pending

- **位置：** `skills/followup/SKILL.md:91-99`；`skills/followup/platforms/boss.md:23-34`；`scripts/ledger.py:608-612`。
- **问题：** 发简历流程只有「请求待同意」分支写 `sent`；直接送达时只写观察事件，未结束发送尝试。
- **触发场景：** 对方已经发来简历请求，Agent 按要求先记 resume/pending，再点击同意；页面直接显示附件送达，不经过我方请求等待同意。按第 5.2 节只追加 observe/resume_delivered，后续该会话一直被判为有未确认外发。不能确认、明确失败的简历分支也没有交代终态。
- **验证：** 本地追加 resume/pending 后追加 observe/resume_delivered，`threads.unresolved` 仍包含该 resume/pending。此结果是脚本验证；页面是否出现直接送达须首次实测确认，但技能自己已支持「同意对方请求」路径，应事先写完整。
- **建议：** 明确「请求发出」和「直接送达」都需为原 attempt 追加 sent，后者再记 delivered；无法确认记 uncertain，明确失败记 failed_no_send。点击前也应像普通回复一样重读会话、检查接管和授权。

### R09 · 重要：非外包的硬条件不符，没有持久化停止推进

- **位置：** `skills/followup/SKILL.md:63`；`docs/design.md:218`；`scripts/ledger.py:593-598`。
- **问题：** 设计要求「不合硬条件」追加停止名单，技能却只在外包时添加；其他硬条件不符只是发一句说明，没有结束状态。
- **触发场景：** HR 明确单休，Agent 发出不符合要求的口径后结束本轮。下一轮没有停止名单和 closed 状态，HR 再问其他问题可能继续代答，L3 也可能重新跟进。回复文字本身不会令脚本把会话标为结束。
- **验证：** 对此类会话仅记录说明性的 reply/sent，`threads` 返回 `closed: null, canFollowup: true`。
- **建议：** 按已确认设计为全部明确硬条件不符写入停止名单；若要改成只结束某个职位或会话，先修改设计并提供相应持久状态。不能用一句拒绝文字代替机器可识别的停止状态。

### R10 · 重要：新 HR 主动来信会被优先当作旧会话，筛选分支无法执行

- **位置：** `skills/followup/SKILL.md:52`、`:59`、`:69-70`；`docs/design.md:216`、`:228`。
- **问题：** 表格要求命中靠前规则就处理，而「本地没有任何记录」覆盖了新 HR 首次主动联系，不仅覆盖旧会话。
- **触发场景：** 一个从未联系过的 HR 发来新职位，且条件明确符合。因本地没有记录，必先命中第 59 行、要求本人交给 Agent，无法到第 70 行按 L2 正常筛选回复。另一个方向上，已有本地记录的招聘者推来新职位并同时索要简历，会先命中第 69 行，也可能跳过新职位筛选。
- **建议：** 先区分「无我方历史的新入站会话」「已有我方历史的旧会话」「已有会话换新职位」，对新职位先完成筛选，再处理消息意图；保留旧会话必须本人交还的规则。

### R11 · 重要：停止名单写入成功，但带逗号或引号的值会静默变形

- **位置：** `scripts/ledger.py:250-264`、`:299-318`、`:745`；`shared/workspace.md:111`。
- **问题：** 写入器使用 JSON 双引号转义，读取器却只去掉首尾引号、不解转义；aliases 又直接按逗号分割，不能读取文档允许的带引号逗号值。
- **触发场景：** 用正常 `stoplist add` 添加别名 `Alpha,Beta`，读回成为两个包含残留引号的别名；添加公司名 `ACME "Labs"`，读回保留反斜杠。之后以原始名称检查，停止名单漏判。`load_stoplist` 的读回校验不会报错。
- **验证：** 两个例子均已复现，写入成功，随后对应公司 `check` 均返回 `allowed: true`。
- **建议：** 让读写共享同一套标量转义与引号内逗号解析规则；不支持的格式应报错。添加「写入 → 读回值完全一致 → 原值 check 必阻止」测试，覆盖逗号、引号和反斜杠。

### R12 · 重要：重新设置与运行中的技能不互斥，可能覆盖期间新增的停止项

- **位置：** `skills/setup/SKILL.md:31-46`、`:50`；`scripts/workspace.py:251-268`、`:284-295`；`scripts/ledger.py:306-318`。
- **问题：** 重新设置先备份、读取，再等待本人确认并写入，但既不检查运行锁，也不检测配置在确认期间是否变化。
- **触发场景：** setup 读取停止名单 S，准备按本人明确要求删除其中的 A；等待确认时 followup 发现风险并追加 B。当前 CLI 没有停止项删除命令，若 setup 根据已确认的旧列表写出 S−A，B 会被一并丢掉。仅使用 stoplist add 追加 A 不会产生这一覆盖路径。若用户只恢复旧备份，restore 也会整体覆盖 stoplist，而非保留备份后新增项。前一种属于并发丢失更新；后一种是当前恢复语义，是否改动需本人决定。
- **依据：** setup 明确「运行锁不动」，各配置写入和 restore 没有持有者检查或版本比较；访谈期间允许发生上述合法交错。这里是静态流程分析，未操作真实重新设置。
- **建议：** 写入阶段与 apply/followup 的配置修改互斥，写前重读并比对自读取以来的变化，只合并已批准修改；若有冲突重新展示差异。可以仅在提交阶段短时锁定，不必在整个访谈期间占锁。备份是回退手段，不能替代防止丢失更新。

### R13 · 一般：工作区体检会把无法使用的问答和简历索引判为正常

- **位置：** `scripts/workspace.py:175-203`、`:224-229`。
- **问题：** qa 检查只检查被识别出的条目；没有识别到任何条目时任意文本也通过。简历检查只查 file 存在，不查 default 是否引用有效版本或 uploaded/use 等运行字段。
- **触发场景：** `qa.yaml` 写入一行普通文字；简历索引的 `default` 指向不存在的版本，但另一个版本的 PDF 文件存在。`workspace check` 返回 `ok: true`，实际 followup 无法可靠选默认简历、无法从问答库取口径。
- **验证：** 使用现有测试夹具的完整虚构工作区，仅改上述两处，体检返回退出码 0、`ok: true`、`qa: 0`、`problems: []`。
- **建议：** 区分明确允许的空库与无法识别的内容；校验简历版本唯一性、默认引用、use、uploaded 的必要结构。体检通过只应表示其承诺检查的结构可用，不必自动判断个人事实真伪。

### R14 · 一般：五秒最小招呼间隔按 pending 时间计算，不能约束实际发送间隔

- **位置：** `scripts/ledger.py:506-515`；`skills/apply/SKILL.md:80`、`:98-107`。
- **问题：** `secondsSinceLastSend` 实际取最后一次 pending 的时间，而非发送完成或确认时间。
- **触发场景：** 第一条先写 pending，页面等待与输入花了 20 秒，随后发送并记 sent；立即准备下一个已选好的候选时，quota 返回不用等待，因此两次真正发送可能不足五秒。
- **验证：** 先写 20 秒前的 pending，再追加当前时间的 sent，立即 quota，得到 `waitSeconds: 0`。
- **建议：** 配额仍按 pending 计数，但发送节奏单独使用最近一次发送确认时间作保守下限；结果不明则按现有规则停发。不要通过随机延时处理这个确定性错误。

## 需要本人决定的问题

这些是策略取舍，不计入上述缺陷数量；不重新讨论已经确认的拆技能、L2 默认和平台风控原则。

1. **排除条件尚未证实时是否允许沟通？** `shared/workspace.md:90` 说未确认排除项「不因此排除」，`skills/apply/SKILL.md:67` 又说关键硬条件无法确认「不自动联系」。对 JD 未写单/双休、未说明是否外包的岗位，需要明确哪些信息必须先证实、哪些可以沟通后核实，避免两个 Agent 给出相反结果。
2. **待决定事项暂停到什么范围？** 是暂停整个会话，还是只暂停面试时间/联系方式等具体动作？确定后把该范围写成字段并执行，不能只写在人读的说明里（R07）。
3. **恢复备份是否回滚后来新增的停止项？** 当前 restore 会覆盖 stoplist；临时样例证实备份后新增项会从当前名单消失，但仍保存在自动生成的 before-restore 备份中。若希望停止项默认保留，应在恢复时合并并展示差异；若希望完整回滚，应在恢复前明确列出将删除的停止项。

## 最小复现材料与后续验证

以下片段在仓库根目录执行，复用现有测试夹具，只创建和清理系统临时工作区，不操作真实求职数据。断言记录的是**当前缺陷行为**，不能直接作为修复后的验收期望。

```sh
PYTHONDONTWRITEBYTECODE=1 python3 - <<'PY'
import sys
sys.path.insert(0, 'tests')
from test_ledger import Workspace

w = Workspace()
try:
    # R05：pending 被 skipped 清除，额度也退回。
    aid = w.greet(final=None, company='状态样例')
    w.append(status='skipped', attemptId=aid, company='状态样例')
    assert w.run('check', '--platform', 'boss', '--company', '状态样例')[1]['allowed']
    assert w.run('quota', '--platform', 'boss')[1]['greetsToday'] == 0

    # R06：非 greet 的未决联系不进入公司去重。
    w.greet(final=None, kind='reply', skill='followup', company='回复样例')
    assert w.run('check', '--platform', 'boss', '--company', '回复样例')[1]['allowed']

    # R08：送达观察不会关闭 resume/pending。
    w.greet(final=None, kind='resume', skill='followup', company='简历样例')
    w.append(kind='observe', observed='resume_delivered', company='简历样例')
    assert w.run('threads', '--company', '简历样例')[1]['threads'][0]['unresolved']

    # R11：写入器能生成读取器无法正确还原的别名。
    w.run('stoplist', 'add', '--name', '别名母公司', '--alias', 'Alpha,Beta',
          '--reason', '测试', '--source', '测试')
    assert w.run('check', '--platform', 'boss', '--company', 'Alpha,Beta')[1]['allowed']

    # R04：失锁后仍可追加新 pending。
    w.run('lock', 'acquire', '--skill', 'apply', '--run', 'old', '--ttl', '0')
    w.run('lock', 'acquire', '--skill', 'followup', '--run', 'new')
    assert w.append(status='pending', runId='old', company='失锁样例')[0] == 0
    assert w.run('lock', 'status')[1]['lock']['runId'] == 'new'
    print('上述缺陷行为均已复现')
finally:
    w.close()
PY
```
