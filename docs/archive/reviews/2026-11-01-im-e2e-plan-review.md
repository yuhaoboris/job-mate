## B：阻断，必须修复后才能开始真实验收

### B1 共享私聊只有成功路径封口；墙钟游标不是可靠的消息隔离边界

**问题与证据**

- 方案:129–132、549–574 只在 P9.5 追加游标；异常流程方案:638–654 卸载、杀进程、检查差异后结束，没有要求失败/中止也封口、保持冻结直到封口成功。方案:543 的「P9 无论结果如何都要做」只出现在 P8，不能清楚约束 P2/P3 已产生真实指令后中止的路径。
- `notify.py:293–294` 的确取所有 cursor 的最大 `int(createTime)`；`593–606` 使用它拉取，并只排除 **小于** 游标的消息。方案:562 用 `date +%s * 1000`，得到当前秒的起点，不是当前精确毫秒，更不是飞书服务端已发送消息的上界。同秒较晚消息或服务端时钟领先时仍会进入下次 poll。
- `notify.py:635` 还会调度已落盘的指令；`327–331` 的待执行指令不受游标限制。若冻结被意外打破并读入消息，再追加更大 cursor 不能消除已经入账的 `command` 或 `received/ready`。
- 方案:554 仅以 `tail -1` 和 `status` 不报错验收，不验证折叠后的游标覆盖范围、原始文件前缀完全不变、是否已有未执行指令；方案:131 把另一台 Mac 同步留到切机时，P9.8 未列出该门槛。

**离线证据**（临时工作区 + FakeIM）

```text
fold minimal cursor: 1234
missing createTime: KeyError
rounded_boundary ['恢复']
persisted_command ['恢复']
none poll: []
restore poll: ['暂停']
```

其中 `rounded_boundary` 放入时间为 `1800000000123` 的恢复消息，追加方案形式的 `1800000000000` 游标，poll 仍执行恢复；`persisted_command` 先持久化尚未 applied 的恢复指令，再追加比它大 10000 毫秒的游标，仍执行恢复。缺 `at`、`note` 不影响 cursor；缺 `createTime` 抛错，不是静默忽略；毫秒为 Unix epoch，无时区换算问题，`at` 仅留痕。

**失败场景**：P3 后因网络或配置失败退出，操作者按「一键回到安全状态」收尾，随后恢复 job-hunt；测试指令在生产执行。即使没有 openItems，指令分支也优先执行（`notify.py:617–629`），可以翻转暂停状态。

**具体修改建议**

- 将封口变成从第一条验收消息产生起就必须完成的 finally/checklist；失败不能跳过，未完成保持两台机器冻结。
- 先停止所有验收消息生产者及 Agent，约定本人停止测试发言；用只读原始消息拉取确认最后测试消息的服务端时间/ID及完整覆盖范围。选择严格大于最后应跳过消息的毫秒边界，例如经核对的最大 `create_time + 1`；不能用本机秒级墙钟替代。封口区间若有真实消息，先逐条对账，不整段丢弃。
- 追加前验证生产账本与基线一致，并明确检查 `pending_commands`，追加时使用 poll/im 互斥或等效独占，校验追加前字节前缀完全一致且只增加一行；追加后用只读 `load_state` 校验 cursor，不运行生产 poll。
- 两台 Mac 同步/各自封口作为解冻前置条件；若已发现生产污染，不能用 cursor 当修复，继续冻结并人工对账。
- 删除「删掉这一行即可恢复原状」（方案:132）的无条件承诺：后续 poll 可能已经推进别的 cursor、落盘消息或执行指令，删除一行不能回滚这些副作用，也可能重新暴露测试历史。

**替代做法的边界**：临时将 job-hunt 的 `im.channel` 改为 `none`，能让新调用的 poll 在 `notify.py:582–585` 返回，降低误拉取概率；**改回后仍会读到积压，不能代替最终游标**，已经加载旧配置的进程也需先停止。代价是新增生产配置写入/精确恢复、暂停真实通知与答复服务、两机同步和快照例外。可作为 D1-A 的额外防护，不是要求推翻 D1；本次未实施。

### B2 五道保险不足以约束真实 Agent，且技能有明确打开浏览器的路径

**问题与证据**

- 方案:122–125 把停止名单、L1、规则和关闭 BOSS 标签列作保险。字段实际是 `authorization.followup.level`（方案:239），确实存在；但 `followup/SKILL.md:36` 明确 L1 **仍执行本人已决定事项**，`apply.send=false` 不能禁止 followup。
- `ledger.py:747–763` 的 `check` 会按公司拦停止名单；`888–892` 的 pending、`830–844` 的 guard 只经 `require_live_lock`，该函数 `1010–1029` 不查授权级别或停止名单。`check` 的拒绝不是后续 append/guard 必须持有的凭证。
- 临时工作区完全采用方案停止名单和授权字段，实测：`check -> allowed:false, exit 1`；同一虚构公司 `append pending -> exit 0`；`guard -> allowed:true, exit 0`。停止名单格式有效，但防线只在调用并遵守 check 的路径生效。
- `followup/SKILL.md:25–32` 读完 rules 后仍列出「准备浏览器，核对账号」；监听器特例 `:40` 只免除其他会话巡检/等待，没有明确免除准备浏览器。默认 `launch_prompt`（`notify.py:812–816`）也没有验收限制。方案:337 直接执行真实 pi，未限制它可用的桌面工具/通用 shell。方案:634 已承认绕过 ledger 的网页点击不受拦截。

**失败场景**：pi 遵照技能准备真实浏览器，或将测试外发决定当作 L1 可执行事项。关闭标签并不撤销招聘账户的登录态或桌面控制能力；P9 看列表属于事后发现，不是事前防止。

**具体修改建议**：保留 D3 的真实 pi，但给本轮配置可验证的能力隔离：只允许测试工作区文件操作、受限的 ledger/notify 命令和 bot↔本人的 IM 路由；禁止桌面/浏览器工具以及通过通用 shell、osascript、HTTP 等旁路操作招聘平台。若不能约束通用 shell，就使用没有招聘平台凭据、不能控制生产桌面的隔离执行环境。仅删掉浏览器扩展但保留任意 shell 不算完成。同步明确 IM-only 场景跳过技能准备浏览器步骤，并在真实唤起提示中写出本轮限制。P7 中性网页探测单独记录其环境与适用边界，不能据其通过解除 P8 的隔离。

### B4 收尾通过判据会漏掉已经 exec 的真实 pi 和脱离进程组的工具

**问题与证据**

- 方案:337 是 `exec "$PI" -p "$1"`。真实启动器 `~/.pi/agent/bin/pi:40–42` 最终也 exec 到 release 下的 pi 程序；运行后进程命令行无需再含 `probes/agent.sh` 或启动器路径。
- P9.3（方案:552）仅杀 `jw-e2e-escape`、搜索 `agent.sh`；异常回退（方案:644–652）用同样的匹配，另建议 `pkill -f "$PI"`，既不能可靠匹配 exec 后的进程，又可能误伤其他会话。P8.3/P9.2 的手动 pi 本来就不受监听器进程组管理。
- `notify.py:891–892` 为子 Agent 建独立进程组；`:900–924` 在停止、超时、异常退出时清理，但正常 exit 0 不走 `_stop_child`。P8.6（方案:534）只记录脱组进程，P9 没有逐个归属/退出确认。
- `service uninstall`（`notify.py:1046–1051`）忽略 bootout 返回码、删除 plist；方案虽另查服务是否存在，但服务不存在仍不能证明独立子进程已退出。

**失败场景**：监听器死亡或卸载后，pi/工具进程仍活着；`pgrep agent.sh` 为空被判收尾通过。其后继续发飞书消息或改测试状态，可能跨过 B1 的封口时刻；广泛 pkill 则可能中断本人其他工作。

**具体修改建议**：每次启动记录本轮 PID、PGID、启动时间与 launch/session 对应关系，手动 pi 也进入独立受管进程组；按归属发 TERM、等待、必要时 KILL，核对该组及已识别脱组子进程全部退出。不能只按命令字符串匹配，也不能杀所有 pi。无法归属/安全结束的进程应阻断解冻。对正常退出留下的工具明确哪些是验收所有、哪些为既有共享服务；P9 同时验证无服务、无 plist、无本轮残留进程/防睡眠断言。

### M2 若干硬判据没有测到声称的对象，或时间界限与实现不符

**证据与失败场景**：

- P8 准备把最后一个 openItem 03 收尾，再新增 07（方案:521、528–529）。监听器可能已进入 idle 300 秒等待（`notify.py:977、1006–1008`），不会因 inbox 文件变化立即醒来；「30 秒内唤起」会把正常实现判失败。P5/P6 的 30 秒还没有为真实 CLI 拉取/回执耗时留余量。
- P4.2 写输出 `hint=...`（方案:452），实际 `public_reply` 字段名是 `decisionHint`（`notify.py:359–361`）。`jwin` 只展示原始 in 行（方案:193–198），不折叠 state；P8.3 要查 ready 必须用 `replies --state ready` 或折叠后的状态，不能据 jwin 的 received 判失败。
- P2.9 只手动请求前两页，却要求看到 2.6(a) 的引用消息（方案:413）。此前测试通知、回复和回执已有多条，引用消息未必在前两页；这也没有执行 `LarkAdapter.fetch` 的 page_size=50 跨页分支（`notify.py:184–212`）。T4 的承诺应区分原始接口分页和适配器真实跨页。
- P6.5（方案:496）把 `kickstart -k` 直接等同于可写 stopped 的优雅停止。本机 `launchctl help kickstart`/`/usr/share/man/man1/launchctl.1:119–121` 只承诺杀掉旧实例再启动，不承诺先给应用完成 SIGTERM 收尾。当前静态证据不能证明该门槛成立。

**建议**：按采样时的 active/idle 状态计算截止时间，必要时先确认监听器已进入 awaiting 周期；明确输出字段和折叠状态查询；分页按目标 messageId 循环到找到，若要宣称适配器跨页已验证，应强制其实际跨页，否则缩小 T4 结论；用明确 TERM 的独立步骤验证优雅收尾，kickstart 单列重启观察，不预设它一定产生 stopped。

### M3 TCC 与锁屏判定越过证据边界

**证据**：方案:327–333 的 tcc 模式运行的是 bash→screencapture/osascript，未运行 pi；P6.4（`:495`）却据此判定「python3→Agent」权限，并将取得前台应用名等同于自动化/辅助功能可用。P7（`:511–514`）5 分钟后解锁再读结果，但 pi 超时可为 25 分钟，没有要求结果必须产生于锁屏区间。

**失败场景**：探针有权限而实际 pi 工具的责任进程不同；或 pi 等解锁才读到 example.com，误报锁屏可操作。该错误结论会误导第二期无人值守设计。

### M4 系统与文件恢复清单不完整，证据默认会写到 E2E 之外

**失败场景**：验收被声称已完全回退，但会话/截图/原始消息仍散落默认目录；权限补开改变了共用生产应用；重复运行覆盖旧证据或既有 plist。当前只读确认 `~/jw-e2e` 和新 listener plist 都不存在，因此“覆盖既有文件”不是已发生的事实。

### M5 真实 Agent 的关键恢复行为仍缺场景，不能把第一期结论写成全覆盖

**证据**：方案:75、299–308、472–478 的假 Agent 直接把 received 改为 consumed，是有意的监听器测试；P8.2/P8.4（`:529、532`）只测新 todo 从 received 正常走完，P8.3 在 ready 后由人工清场。没有真实 pi 从**预先存在的 ready** 恢复，也没有 `ledger decision=done` 但结果通知/consumed 尚未补齐的真实技能场景。这些是设计:274、followup:52–60、108–117 明确承诺的路径。P8.2 的 T18 附加只验证同正文去重，没有验证新结果版本允许新通知。

**失败场景**：pi 正常 todo 处理通过，但恢复时重解释旧回复、重做已完成决定或错误消费；假 Agent 自动标 consumed 掩盖不了也测不到这些行为。后续若拿第一期作为生产恢复能力证明，会高估验证范围。

**建议**：增加纯合成、无真实会话的两组夹具：预存 ready + 稳定 inbox 结论（原话故意与已落盘结论可区分），以及 done + ready + 待补结果通知；由真实 pi 只恢复并收尾，核对不重解释、不新增外发。T18 另测正文 A 重发去重、正文 B 新发一次并再次去重。若不加，报告明确这些真实 Agent 路径未覆盖，不能宣称已验收。不必扩大到真实 HR 外发、长时间断网或多机并行。

### L2 证据采集管道没有统一保留真实退出码
