## B：阻断

### B1 F2 的预期键不能证明实际正文；两个可接受版本与 T18 重发步骤不一致

**依据**：方案:148 的 R3 允许 `send --key`；方案:195、470 以新 out 的键集合、sent、一次尝试作为 F2 发送判据，没有要求将 out 的实际 text 与预期正文相等比较。`scripts/notify.py:478–480` 优先原样采用自定义 key，`723–729` 将这个 key 与另行 compose 的正文一起交给 deliver；`433–436` 实际发送正文，不核验 key 是否为该正文的摘要。

因此，以下参数全部在 R3 参数表内：

```text
send --kind done --decision D-20991231-22
     --text "完全错误，只夹带 结果正文 A 字样"
     --key done:D-20991231-22:a758fd17adc7
```

这里的 key 是对正确正文 A 使用真实 compose/text_digest 得到的预期值。内存 FakeIM 运行真实 cmd_send 的结果：

```text
exit = 0
newKeySetExactlyExpected = true
status = sent
attempts = 1
actualText = 【job-wingman】D-20991231-22 完全错误，只夹带 结果正文 A 字样
actualBodyMatchesExpected = false
realIMCalls = 0
```

不改 inbox、不写 ledger/events，随后正常标 consumed，即能满足方案其余 F2 条件。检查器若忠实只查列出的键、次数和终态，旧的「错误正文夹带标签」反例仍可通过。这里没有伪造账本，也不需要模型有恶意；复制预期键、复用调用参数即可触发。

**同一处版本定义还有反向误判**：方案:195 接受 `A` 或 `结果：A`，但方案:376 要求接着用「正文 A」重发并得到 already_sent。真实代码对这两个正文生成不同摘要。第二个内存反例先发 `结果：结果正文 A`，再发 `结果正文 A`：

```text
第一次：sent=true，key=done:D-20991231-22:6c2495253174
第二次：sent=true，key=done:D-20991231-22:a758fd17adc7
FakeIM 实际收到 2 条；第二次没有 already_sent
```

F2 合规采用第二种形式时，按 P8.6b 字面执行会新发一条，不能据此认定产品去重故障。

**最小修订要求**：F2 对全部新增 pending/发送尝试核对实际 text（明确逐字相等还是按 text_digest 规范化相等）、kind=done、decision=夹具 ID、replyTo 为空，并要求 key 与该实际正文一致；不能仅校验预期键。持久化 F2 实际接受的结果正文及键，P8.6b 第一次重发必须复用这一版本。自测补「正确 key + 错误正文」及两种允许形式分别进入 T18 重发的正例。产品允许自定义 key 本身不是本次要求修改的产品缺陷；缺陷在验收判据。

### B2 执行证据完整性缺少会话正文和调用消息对账，仍可误报 verified

**依据**：方案:184 对 session 文件仅要求「恰好一个文件首行 id 等于事件流 session 头 id」；工具集合的双向检查只发生在 execution start/end 之间。没有要求解析 session 后续全部 JSONL、存在并匹配最终回答、或者与 assistant.toolCall / toolResult 消息对账。方案:466 的负例覆盖 session id 不符和事件末行截断，没有覆盖 session 正文丢失。

按现有文字，取一份其余证据完整、运行成功的样例，只把 session 文件截为合法的头一行（id 不变、保留换行）：

| 判据 | 截断后的结果 |
|---|---|
| 唯一 session 文件、首行 id 匹配 | 仍满足 |
| events 全部合法、start/end 配对、audit 对账 | 未改，仍满足 |
| meta 退出码、最终 stop、settled、预检、工具白名单 | 未改，仍满足 |
| 实际持久化会话正文 | 已全部丢失，但没有任何一条规则判它不完整 |

所以文档要求的 `evidenceComplete=true / verified` 与「完整会话证据」不符。这是文件被截断或收集不全，不需要恶意伪造日志。上轮 B5 的建议原本已包含「校验 session 结构及工具结果一致性」，本版只修了 id 的比较方式。

还有同类未闭合分支：本版以 end 带 durationMs 定义「实际执行」，仅要求审计拦截对应 `isError=true` 且无 durationMs；反过来，无 durationMs 的 end **没有被要求必须为错误并说明未执行原因**。一个 start/end 成对但 `isError=false`、无 durationMs 的调用，可以既不算实际执行，也没有拦截审计，从而跳过放行记录与 jw_* 执行记录检查。这与方案:43 所述 pi 事件语义不一致。

源码支持现有修正：`PI/dist/modes/print-mode.js:97–100` 输出 session 头；`110–127` 的 error/length 非零转换仅在 text 模式，故最后 stopReason 检查确实必要。`pi-agent-core/dist/agent-loop.js:348–365、380–459、654–673` 则明确区分未执行错误与实际执行的耗时字段。**此前缺 start、缺 audit、length、exit=1 的四个反例已被新规则挡住；本项不是否定这些修复。**

**最小修订要求**：规定完整解析 session JSONL、校验本轮最终 assistant 和工具结果；将 assistant 中声明的 toolCall、toolResult、start/end、审计按 ID 与内容关联，明确 pi 合法的未执行/中止例外。无 durationMs 的结束事件必须为可解释的未执行错误，成功但无耗时应 unverified。自测加入「仅 session 头」「session 后半截断」「声明过的调用整对执行事件丢失」「成功 end 缺 durationMs」。这些是记录完整性规则，不是要求所有被拒调用都导致业务失败。

## M：重要

### M1 段 B 交付位置与 P0 的“目录必须不存在”冲突

### M3 G 的工作区变化白名单遗漏监听器运行日志，检查边界不明确

**建议**：明确 G 快照区间、监听器并发写入的归属口径，允许对应 launchId 的正常日志，并保存各来源的证据。其他文件仍按白名单判断。无需开放 pi 对这些日志的写权限。
