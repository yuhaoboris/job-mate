# 独立评审说明

> 历史归档：保留当时的版本、结论与行号；文件引用已按当前目录更新，私人标识和本机路径已脱敏。本文不代表当前实现或验收状态，当前状态见项目的 `docs/status.md`。

给评审 Agent 使用。目的：在实测之前，独立找出 job-wingman 初版的缺陷。

## 约束

- **只读评审**：不修改仓库内任何文件，唯一例外是把报告写到 `docs/reviews/<日期>-<评审者>.md`。
- **不访问招聘平台**，不打开 BOSS 直聘，不发送任何消息。
- **不修改 `<求职工作区>`**。需要看真实工作区的样子时可以只读查看，其中是本人的真实求职数据，不得复制进报告或外传；报告中引用时只写字段名和结构。
- 运行测试可以：`python3 -m unittest discover -s tests`。用临时目录试 `scripts/*.py` 可以，不要指向 job-hunt 执行会写入的命令（`append`、`lock`、`stoplist add`、`migrate`、`init`、`backup`、`restore`）。

## 先读

1. `AGENTS.md`：项目约定。
2. `docs/design.md`：设计。第 1 节和 `AGENTS.md`「约定」中的原则已由本人确认（如按授权和风险拆技能、不模拟人工、不规避平台检测、`followup` 默认 L2）；可以指出它们带来的问题，但标为「建议」，不作为缺陷。
3. `skills/*/SKILL.md`、`skills/*/platforms/boss.md`、`shared/`、`scripts/`、`tests/`。

## 评审重点

按重要性排列：

1. **不重复外发**：`pending` → 终态的流程、`ledger.py check` 的阻止逻辑、锁过期接管、中断恢复。找出任何会导致同一职位或会话被发送两次的路径。
2. **授权与承诺边界**：`followup` 是否有路径会越权，例如点了交换联系方式或面试邀约卡片、在 L1 下发送、对本人接管的会话发送、答应面试时间或薪资数字。
3. **技能能否执行**：假设一个只读这些文件的 Agent 第一次运行，它会不会卡住、遇到歧义、或碰到前后矛盾的指令？相对路径、命令参数、步骤顺序是否说得清？
4. **文档与代码一致**：`shared/ledger.md`、`shared/workspace.md` 描述的行为与 `scripts/ledger.py`、`scripts/workspace.py` 实际行为是否一致；技能里调用的命令和参数是否真实存在。
5. **`setup` 重新设置**：能否安全升级旧工作区，会不会丢失停止名单、事件记录或本人的配置。
6. **规则遗漏**：`apply` 的筛选与排序、`followup` 的分诊表，有没有常见场景没覆盖或处理不当。
7. **隐私**：记录、inbox、通知中是否可能写入不必要的个人信息或聊天全文。
8. **代码质量**：`ledger.py`、`workspace.py` 的边界情况（时区、跨日、并发写入、损坏行、停止名单解析、公司名匹配误伤或漏判）和测试覆盖的缺口。

## 已知未做，不必报告

- `scripts/build.py`（独立技能 zip）、`package.json`（Pi）、CI。
- 推送通知的具体配置（本人决定在 `followup` 跑顺后再配）。
- 尚未在 BOSS 上实测：`apply` 实际发送、`followup`、`setup` 重新设置。`apply` 只筛选已在 Codex 中跑通一轮。

## 报告格式

写到 `docs/reviews/<YYYY-MM-DD>-<评审者>.md`：

1. 一段总体结论：能否进入实测，最大的风险是什么。
2. 问题列表，按严重程度排序（严重 / 重要 / 一般 / 建议）。每条包含：
   - 位置：`文件:行号`
   - 问题：一句话
   - 触发场景：什么输入或状态下会出错，结果是什么
   - 建议：怎么改
3. 需要本人决定的问题（涉及产品取舍、不是对错的）。

只报告有把握的问题；拿不准的标「待确认」并说明需要什么信息才能确认。
