状态：2026-11-02 第三版，红队审查通过（第三轮必改项 R1–R6 与收口核对指出的 R3 问题均已修订）。第一、二版都没有通过红队审查。第二版试图在页面上把会话的全部历史条数和本人插手过的地方数清楚，红队指出这在 BOSS 页面上做不到可靠，每补一处又引出新的漏洞。本版改用更简单、更保守的模型（第 1 节 D4、D5），三轮意见的对照见第 14 节。实现完成后，规则并入 `docs/design.md` 第 8 节，本文件只作追溯。

## 0. 目标与现状

**目标（本人提出）**：用户开始使用 job-mate 之前就沟通过、现在仍在消息列表中的会话（下称「旧会话」），也能加入 `followup` 的跟进队列。

**现状与问题**（2026-11-02 真实运行：本人在 IM 中要求「往下找已读未回、送达未看的消息，主动跟进」，Agent 回复「未登记的旧会话不能自动跟进」）：

| # | 问题 | 位置 |
|---|---|---|
| P1 | 没有外发记录的会话，`followup_eligibility` 一律返回「我方尚未发出过消息」；完全没有记录的会话，`check --kind followup` 按 `no_thread` 拒绝。观察事件（`released` 等）不会产生 `lastOutbound`，也带不进历史 | `ledger.py` `followup_eligibility`、`conversation_reasons` |
| P2 | 分诊只覆盖「HR 有未答消息」的旧会话。**我方最后发言**的旧会话（已读未回、送达未读）既不发送也不上报，本人也找不到交给 Agent 的入口 | `followup/SKILL.md` 第 4.1 节 |
| P3 | 判断本人接管的规则是「我方消息不在记录里，并且晚于最近一条本地外发」。没有本地外发的会话，页面上所有历史消息都会被判成本人回复。本人接管后交还（`released`）时，接管期间本人发的消息同样晚于最近一条本地外发，会立即再次判成接管（所有会话都有这个问题） | `followup/SKILL.md` 第 4.3 节、`platforms/boss.md` |
| P4 | 跟进礼仪只统计 ledger，旧会话页面上已有的跟进不计入 | `followup_eligibility` |
| P5 | IM 只能对已有事项作决定，不能新增授权，本人在 IM 里的要求没有可批准的入口 | `shared/notify.md` |
| P6 | 汇报不说明是哪些会话、为什么、本人能做什么 | `followup/SKILL.md` 第 9 节 |
| P7 | 一个决定涉及多个会话时，只要有一条 `unpaused` 就判为完成：`cmd_decision` 返回 `done`，`unstepped_decision_attempts` 返回空，于是其余会话一直暂停，「无步骤编号外发」的阻断也失效 | `ledger.py:769–775,794–797` |
| P8 | 判断本人接管时只看文字消息。本人在平台上点「同意」交换联系方式、接受面试、发简历，都不会被识别（所有会话都有这个问题） | `followup/SKILL.md` 第 4.3 节 |

## 1. 决定

| # | 决定 |
|---|---|
| D1 | 新增「**登记**」动作（`observe/adopted`）：旧会话第一次交给 Agent 时写入一个简化的基线，之后它就是已登记会话，按现有规则处理 |
| D2 | 登记按 `authorization.followup.legacyThreads` 处理：`auto`（缺省）/ `ask` / `off`。2026-11-02 本人决定缺省改为 auto；缺少字段按 auto，setup 补缺省时写 auto，本人可以改成 ask / off，已有设置不变 |
| D3 | `ask` 模式下，候选会话汇总成**一条**批量「待决定」事项，经 IM 发送；答复只对事项里列出的会话生效 |
| D4 | **旧会话使用固定的跟进额度**：`limits.legacyFollowupBudget`，缺省 1，可设 0–3（2026-11-02 本人确定）。登记后最多再主动跟进这么多次。我方已经连续 3 条以上没得到回复的旧会话，不再跟进。之所以不按历史计数，是因为页面上无法可靠地数清以前跟进过几次。礼仪的其他规则（每天 1 次、连续 2 次未回停 7 天）照常适用 |
| D5 | **用时间分界判断本人接管**：分界取「登记时开始读取页面的时刻、最近一次交还、最近一条本地外发」中最晚的那个（第 7.2 节）。页面时间按区间比较：分界之后出现的、对应不上本地记录的我方活动（文字或卡片操作）都视为本人接管；跨过分界、无法判断的，暂停并问本人。分界之前的都是历史，不比对内容，也不在 ledger 中保存原文。这一条同时修复所有会话的 P3、P8 |
| D6 | 只有 L3 才查找我方最后发言的旧会话。HR 有未答消息的旧会话在所有级别都按原规则处理，本人交给 Agent 时同样走登记 |
| D7 | **只有没有遗留问题的会话才是候选**。职位待确认，或者历史中有没了结的需要本人决定的事项，都不进入批量事项，只在汇报中列出，由本人自己处理或在终端里明确交给 Agent。所以「纳入跟进」只表示交给 Agent 按现有规则处理，不会顺带解除任何限制 |
| D8 | 本人在平台上亲自发的消息不计入 Agent 的跟进次数。这是现有会话本来的规则，旧会话沿用 |

不变：跟进礼仪的其他数值、`activeHours`、发送前统一检查（第 5.0 节）、`pending` / `guard` 流程、风控遇限即停、不使用 CDP / Playwright、IM 不能新增授权。

## 2. 基线

### 2.1 读取范围

有两种读取，范围不同，**不能互相替代**：

| 读取 | 用途 | 范围 |
|---|---|---|
| **基线读取** | 计算第 2.2 节的字段 | 从会话末尾往上读，满足任一条件即停：读到 HR 的一条文字消息；读到会话的第一条消息；已经数出我方连续 3 条文字消息 |
| **分诊读取** | 第 4 节的风险、职位、遗留事项检查 | 沿用第 3 节第 3 步的原规则：从我方第一条消息或最近 20 条消息起读，包括请求卡片；看到未了结事项的线索时继续往前追溯 |

开始读取页面之前，先记下当时的时间作为 `readAt`（第 7.2 节用它作为接管分界，不用写入记录的时间）。读取失败、加载不出来，或者分不清哪条是我方发的，这一轮就不登记，在汇报中写「历史未能读取」。

**只有卡片、没有任何文字消息**的会话不是候选，在汇报中列出。

### 2.2 字段（`baseline` 对象）

| 字段 | 类型 | 含义 |
|---|---|---|
| `readAt` | ISO 时间 | 开始读取页面的时间（2.1 节） |
| `lastSpeaker` | `us` \| `hr` | 最后一条文字消息是谁发的 |
| `trailingOur` | 整数 0–3 | 最后一条 HR 文字消息之后，我方文字消息的条数，数到 3 为止。读到会话开头都没有 HR 文字消息时，从会话开头算起 |
| `lastOurAt` | ISO 时间 \| `null` | 我方最后一条文字消息时间的**上界**（页面只显示日期时取当天 23:59:59）。`null` 表示**基线读取范围内没有读到**，不代表从未发过 |
| `lastHrAt` | ISO 时间 \| `null` | HR 最后一条文字消息时间的上界。`null` 的含义同上，不代表 HR 从未发过 |
| `lastOurState` | `delivered` \| `read` \| `null` | 我方最后一条消息的送达状态；`lastSpeaker` 为 `hr` 时为 `null` |

`adopted` 事件另外带 `followupBudget`（整数 0–3），值取登记时 `profile.json` 中的设置。以后修改这个设置，不影响已经登记的会话。

校验规则：

- `lastSpeaker` 为 `hr` 时：`trailingOur` 必须为 0，`lastOurState` 必须为 `null`，`lastHrAt` 不能为 `null`。`lastOurAt` 可以为 `null`：基线读取读到 HR 的消息就停了。这时会话没有 `lastOutbound`，在 Agent 回复之前不会主动跟进，这是保守的结果。
- `lastSpeaker` 为 `us` 时：`trailingOur ≥ 1`，`lastOurAt` 不能为 `null`。`lastHrAt` 可以为 `null`：数到 3 条就停了，或者 HR 从来没发过。
- `readAt` 不能晚于事件写入时间。

### 2.3 计入礼仪（`build_threads`）

| 线程字段 | 取值 |
|---|---|
| `followupsSent` | `trailingOur ≥ 3` 时取 3（视为已经用完）；否则取 `3 - followupBudget` |
| `followupsSinceReply` | `lastSpeaker` 为 `us` 时取 `trailingOur`，**连第一条也算**（宁可多算）；为 `hr` 时取 0 |
| `lastFollowupAt` | `lastSpeaker` 为 `us` 时取 `lastOurAt`，否则为 `null` |
| `lastReplyAt` | `lastHrAt` |
| `lastOutbound` | `lastOurAt` 不为 `null` 时取 `{"kind": "legacy", "at": lastOurAt}` |

`followup_eligibility` 不改。`followupsSent` 里的 `3 - followupBudget` 只是占位值，用来表示额度，不是实际发送的次数。所以 `threads` 对登记过的会话另外输出 `legacyBudgetLeft`（剩余额度）和 `followupsSinceAdoption`（登记后实际跟进的次数），汇报只用这两个字段，不能说「已经跟进 3 次」。

按缺省额度 1 计算的结果（红队已用现有 `followup_eligibility` 验证）：

| 旧会话状态 | 结果 |
|---|---|
| 我方 1 条（招呼），HR 未回 | 满足页面条件后可以跟进 1 次；当天发过招呼的，当天不跟进 |
| 我方连续 2 条，最后一条在 7 天内 | 冷却中，暂不跟进 |
| 我方连续 2 条，最后一条超过 7 天 | 可以跟进 1 次，之后额度用完 |
| 我方连续 3 条及以上 | 不再跟进 |
| HR 最后发言 | 由第 4.3 节处理 HR 的消息；之后我方未得到回复时，可以跟进 1 次 |
| `legacyFollowupBudget: 0` | 只登记，不主动跟进（L2 代答照常） |

### 2.4 隐私

`baseline`、`reason`、`evidence`、inbox 和 IM 中都不写消息原文。`reason` 写判断结论，例如「旧会话：HR 未回复，我方 1 条，已读」。`evidence` 写可以核对的元数据，例如「读到会话开头；末条 10-20 已读」。

## 3. 查找旧会话（followup 第 3 节新增一步）

### 3.1 前提

| 本轮状态 | 查找 | 写 ledger / inbox / IM |
|---|---|---|
| 全局暂停（安全验证、登录失效、本人「暂停」） | **不查找**，不浏览平台 | 否 |
| 本轮显式禁发（「只看看」） | 只读查找 | 否，只在汇报中列出 |
| L3，`legacyThreads` 为 `ask` / `auto` | 查找 | 是 |
| L1 / L2，或 `legacyThreads: off` | 不查找我方最后发言的旧会话 | — |

### 3.2 本地状态分类

用 `ledger threads --company <公司> --recruiter <姓名(职务)>` 查找时，**只有公司名精确匹配、招聘者也一致才算同一个会话**。只是疑似匹配的不点开，在汇报中列为「身份不确定」。

| 本地状态 | 分类 |
|---|---|
| 有 `adopted`，或有状态为 `sent` 的动作尝试 | 已登记，跳过 |
| 有 `pending` / `uncertain` 的尝试 | 有未确认的外发，跳过（第 4.3 节原规则） |
| 已关闭、本人接管（`manual`）、等待决定（`pausedBy` 非空） | 跳过 |
| 没有记录；或者只有 `already_contacted` / `skipped` / `failed_no_send` 的尝试和其他观察事件 | **未登记**，进入第 4 节 |

`apply` 记过 `already_contacted` 的会话，正是「以前就联系过」的旧会话，可以登记。

### 3.3 步骤

1. 先按原顺序处理未读会话和 `canFollowup` 为 `true` 的会话，再查找旧会话。
2. 在「全部」列表中向下滚动，逐项按 3.2 节分类。
3. 列表摘要显示 HR 最后发言的，按第 4.1 节原规则处理。显示我方最后发言（`[送达]` / `[已读]`）的，才点开。
4. 停止条件，满足任一即停：连续 3 个非置顶项早于 `limits.legacyMaxAgeDays`（缺省 30 天，置顶项不参与判断）；本轮已点开 `limits.legacyScanPerRun`（缺省 20）个旧会话；到达列表底部；遇到任何风控提示（按 `safety.md` 停止整轮）。
5. 停止名单命中、`check` 返回 `rejected` / `risk` 的公司不点开。
6. 每处理完一个会话 `notify poll` 一次；运行超过 30 分钟时 `lock renew`。

## 4. 旧会话分诊

点开后先按 2.1 节做**分诊读取**和**基线读取**，再**逐项检查以下全部类别**，不因前面某项命中就跳过后面的项（A、B 除外，它们直接结束这个会话）：

| 类别 | 判断 | 结果 |
|---|---|---|
| A 风险 | 第 4.3 节的风险信号 | 按原规则：`observe/risk` 加停止名单，写入 inbox。**结束** |
| B 对方结束 | 页面**明确显示**对方拒绝，或职位已关闭、已下线 | 记 `observe/rejected` / `observe/job_closed`。**结束** |
| C 职位 | 打开关联的职位详情，按 `apply` 的条件评估 | 公司层面不符（人员外包、劳务派遣）：`observe/declined` 加停止名单。职位层面明确不符：`observe/declined`。**待确认：不是候选** |
| D 遗留事项 | 历史中有没了结的需要本人决定的事项：面试邀约、地点 / 驻场 / 出差、薪资数字 / Offer、交换联系方式、问「是不是 AI」 | **不是候选** |
| E 时间 | 我方最后一条消息不满 1 小时 | 这一轮跳过 |
| F 读取 | 2.1 节读不出来，或者只有卡片 | 这一轮跳过 |

- 职位详情**读取失败**（加载失败、空白页）不能当作职位关闭，这一轮跳过；登录失效、访问限制按 `safety.md` 停止整轮。
- A、B、C 写入的观察事件都带 `tags: ["legacy"]`，`reason` 以「旧会话：」开头。
- 只有 C 评估为「符合」、D 没有命中、E 和 F 都通过的会话才是**候选**。C 待确认和 D 命中的会话，在汇报中列出原因，**不写 ledger**。下一轮还会再查到它们；汇报中按「仍需你处理」列出，不重复发 IM。

## 5. 授权与入口

| 来源 | 候选 |
|---|---|
| `legacyThreads: auto`（缺省） | 直接登记（第 7 节，`skill: followup`，`reason` 写「legacyThreads=auto」） |
| `legacyThreads: ask` | 第 6 节批量事项 |
| 本人在终端本轮指令中要求（「把旧会话也跟进」） | 本轮按 `auto` 处理，不写回 `profile.json` |
| 本人在终端点名某个会话（「把 X 交给 Agent」） | 登记（`skill: user`，`reason` 引用本人原话）。「交给 Agent」**只表示交出处理权，不放宽任何条件**：C 类待确认的会话，只有本人明确说了这个条件不限制、或者允许例外时才登记，否则先在终端问清楚，问不清就不登记；D 类的遗留事项，登记时先按第 6.2 节的方法写 `paused` 和 inbox，再处理 |
| 本人在 IM 中用自由文本要求 | 不新增授权。回复明确对应到一条未决的批量事项（引用了那条通知，或写了决策 ID），并且只是在事项列出的会话里作选择时，按事项答复处理；要求长期授权或扩大范围时，用 `clarify` 说明：长期设置在 `setup` 中修改，本轮可以在终端发起 |

HR 有未答消息的旧会话（第 4.1 节原规则），本人决定交给 Agent 时：原来记 `observe/released`，改为按第 7 节登记，基线取执行时的页面。

## 6. 批量待决定事项

### 6.1 建立

1. 一个事项最多 10 个会话。inbox 中已经有一条未决的旧会话事项时，不再新开，新候选留到之后的轮次。
2. 成员按发现顺序编号为 A、B、C……。用字母，是为了不与 `notify` 的数字序号冲突。同一个决定里，一个字母只对应一个会话，一个会话也只有一个字母；`ledger` 校验这两点。
3. **先**给每个成员记 `observe/paused`：带同一个 `decision`、`member`、`baseline`、`title`、`tags: ["legacy", "legacy-batch"]`，`reason` 写 inbox 中那一行要用的脱敏摘要。**全部写完后**才写 inbox、发 IM。
4. inbox 每行写：编号、公司 / 岗位 / 招聘者、我方最后一条的日期与状态、我方连续未回的条数、登记后可以跟进几次。正文不写消息原文。
5. 选项：「全部纳入」/「只纳入 A、C」/「都不纳入（留给我自己）」。事项中注明：纳入只表示交给 Agent 按规则处理。回复对不上编号或含义不清时，用 `clarify` 追问。
6. 恢复：第 2.1 节对账时，凡是带 `legacy-batch` 标签、但 inbox 中找不到的决定，用 `ledger decision` 返回的 `members`（编号、公司、岗位、招聘者、基线、`reason`）重建事项，再发 IM。

### 6.2 执行（第 2.2 节）

每个成员分三步，按顺序做。`ledger decision --id <ID>` 的 `members[]` 显示每个成员做到了哪一步：

**第一步：登记或留给本人**（`members[].result` 已经不为 `null` 的成员跳过这一步）

| 本人选择 | 执行前重读页面（2.1 节两种读取，重新记 `readAt`） | 动作 |
|---|---|---|
| 纳入 | 页面上有我方活动的时间区间**晚于或可能晚于**该成员 `paused` 事件的 `baseline.readAt`（第 7.2 节的区间比较，含模糊），并且对应不上本地记录 | 记 `observe/manual`（带 `decision`、`member`）：本人在这期间可能亲自处理过，不登记。结果通知中说明，本人可以再交给 Agent |
| 纳入 | 其他情况，包括 HR 发来了新消息 | 记 `observe/adopted`（带 `decision`、`member`，`baseline` 取这次重读的结果，含新的 `readAt`） |
| 纳入 | 页面打不开、读不出来 | 这一轮不处理这个成员，事项保持 `partial`，下一轮继续 |
| 不纳入 | 不需要重读 | 记 `observe/manual`（带 `decision`、`member`，`reason` 引用本人原话） |

**第二步：登记后分诊**（只针对 `adopted` 的成员）

按第 4.3 节判断这个会话现在是否需要本人决定，例如 HR 新发来面试邀约或薪资问题。需要时，先记新的 `observe/paused`（新的决策 ID），再写 inbox。这一步**只判断要不要暂停，不发送**；回复 HR 留到批量事项完成后，按正常流程处理。

**恢复时不能跳过这一步**：成员的 `result` 是 `adopted`、但还没有这个批量事项的 `unpaused` 时，一律重读页面、重新分诊。会话已经被别的决定暂停（`pausedBy` 里有其他 ID）时，说明上一次已经暂停过，不重复暂停。

**第三步：解除批量暂停**

只有第一步有了结果、第二步也完成（需要暂停的已经确认新的 `paused` 写入）之后，才给这个成员记带该 `decision` 的 `observe/unpaused`。全部成员都解除后，事项就是 `done`（第 8 节）。

事项本身没有外发步骤，不写 `pending`。

## 7. 登记、交还与接管

### 7.1 `observe/adopted`

- 必须带 `baseline`（2.2 节）和 `followupBudget`；可以带 `decision`、`member`。
- **必须在有效运行锁内写入**：复用 `require_live_lock`（会同时检查锁是否过期、本轮是否禁发、是否全局暂停），与 `pending` 一样在 `lock_mutex` 内完成「读记录—判断—追加」，避免两个进程同时登记同一会话。
- **先判断是否重复**：会话已经有 `adopted` 时，新的登记不写入，返回 `duplicate: true` 和已有的那条登记，第一次登记的时间、额度和基线都不变。`decision`、`member` 与已有登记相同时，视为同一操作重试成功；不同时输出 `conflict`，退出码 1。技能不能把 `conflict` 当成这个成员已经登记，要在汇报中列出，请本人核对。
- **不重复时，按下面的准入规则判断**。这是写入时的规则，和第 3.2 节查找时的跳过规则不同：

| 会话状态 | 能否登记 |
|---|---|
| 有状态为 `sent` 的动作尝试 | 不能：已经是已登记会话 |
| 有 `pending` / `uncertain` 的尝试 | 不能：先核对未确认的外发 |
| 已关闭（`closed` 非空） | 不能 |
| `pausedBy` 中**只有**本事件自己的 `decision` | 能（批量事项的成员）；这个暂停不会因为登记而解除，要等第 6.2 节第三步的 `unpaused` |
| `pausedBy` 中有其他决定 | 不能 |
| 本人接管（`manual`） | 只有 `skill: user`（本人明确交出）时能，登记同时解除 `manual`；`skill: followup`（`auto` 或批量事项）不能，也不会解除 `manual` |
| 其他（没有记录；只有 `already_contacted` / `skipped` / `failed_no_send` 和观察事件） | 能 |

  表中的条件**同时判断**：例如「只被本事项暂停」不能越过 `manual`、已关闭、未确认外发的检查。不能登记时报错（退出码 2），并给出原因。

### 7.2 接管分界（所有会话）

**分界时刻 `boundaryAt`**：`threads` 新增这项输出，取下面几项中最晚的一个：

- 最近一条本地 `sent` 外发的时间；
- `adopted` 的 `baseline.readAt`。**不用**事件的写入时间，这样读完页面到写入记录之间本人发的消息不会被当成历史；
- `released` 的事件时间（本人明确交还，交还前本人发的消息本来就应该当作历史）。

**页面时间按区间比较**：页面显示「10:00」表示 [10:00, 10:01)，只显示日期表示当天全天。

**判断页面上的每一个我方活动**（文字消息，以及发简历、同意交换联系方式、接受面试等卡片操作）：

| 情况 | 结论 |
|---|---|
| 能对应到一条本地 `sent` 记录：同类（文字比对 `outboundTexts`，简历卡片对应 `resume` 尝试），并且记录时间落在页面时间区间前后 2 分钟内。比对所有本地记录，**包括构成分界的那一条** | Agent 发的，正常 |
| 对应不上，时间区间整个早于 `boundaryAt` | 历史，正常 |
| 对应不上，时间区间整个晚于 `boundaryAt` | 本人亲自处理过：记 `observe/manual` |
| 对应不上，时间区间跨过 `boundaryAt`（同一分钟，或者只显示日期并且是同一天） | **无法判断**：这个会话本轮不发送，写入 inbox「待决定」：「这条是你发的吗？」选项为「是我，我来处理（记 `manual`）」/「交给 Agent 继续（记 `released`）」。暂停这个会话（`observe/paused`），等本人决定 |

本人选「交给 Agent 继续」时，记 `released`，**分界不往后推**：`boundaryAt` 仍取事件时间，不能取未来的时刻。同时在事件里记下本人确认过的那几条模糊活动 `acknowledged`：按页面显示的时间标签分组，记活动类型和条数，例如 `[{"shown": "2026-11-02", "precision": "day", "kind": "text", "count": 1}]`。不记原文。

之后判断跨过分界的我方活动时，同一个时间标签、同一类型的活动，按页面上从早到晚的顺序，前 `count` 条视为本人确认过的历史；多出来的，仍按上表判为无法判断（时间区间跨过分界）或本人接管（时间区间整个晚于分界）。例如上午 10 点按日期标签确认了 1 条，下午本人又发了一条显示「14:00」的消息：这条消息整个晚于分界，判为本人接管。如果它也只显示日期，就是同一标签的第 2 条，超出确认的条数，判为无法判断，再次暂停询问。

这条规则同时修复所有会话的 P3、P8。对于已经存在的会话，同一分钟内的时钟误差、事后补记 `sent` 等问题本来就存在，本方案没有让它们变得更糟，记为已知局限。
